# Original UI Consumption and Screen Change from Active HUD Touch

Follow-up [bw487](active-hud-touch-family-contract.md) also verified actual UI consumption and scrolling for stock 2.3 and Faceclaw with input/no-input pairs. The following is evidence and root-cause analysis from the initial stock24 integration.

bw-0486. **An additional touch in original stock 2.4 main led to UI command handling and return, then screen scrolling.** A no-input control with the same original, model, and observation script retained the screen. Other firmware and ring support in E11 as a whole were not complete, so progress remains **14/16=87.5%**.

## Cause and correction

[bw485](active-hud-input-integration.md) reused existing screen-open response 2 for the channel 2 display command. The original channel 2 receive branch generates response 2 for request type 1 and **response 4 for type 3**. Type 3 handling constructs 4 at `0x4664bc`, sends it at `0x4664e4`, then calls the UI command producer. The transmitting master callback also follows `0x46971c→0x445f5c` on response 4. Response 2 produces a different UI queue type.

The earlier run was preserved as failure evidence. The new test changed the command response to 4 and added observation points at actual consumption boundaries. Responses use request ID/CRC and apply only to exact payloads confirmed in source. PC, TCB, branches, returns, and guest SRAM are not forced. This is an explicit virtual UART peer, not execution of the actual opposite glasses.

## Actual original execution

Input is an existing reloadable IOM5 touch report and GPIO27 250 µs low waveform, not a measurement of the physical MCU. The run waited 400 ms after the first screen and observed for 200 ms.

`GPIO27 → original input task → source1/code4/10/167 → service108 callback → channel3 request/response8 → UI type7 parser → channel2 type3 request/response4 → UI command queue → app1 event3 → original command handler → callback cleanup → new frame`

Original event 3 received a 6-byte command in actual UI TCB/Thread mode. The handler received the same pointer/length and returned to the callback cleanup point. `0044a7000a00` in the final original buffer matches the command and scroll value. This compares the final buffer; it is not claimed as a history of every transient write.

| Item | Touch input | No-input control |
| --- | --- | --- |
| Starting screen raw SHA | Same | Same |
| Additional reports consumed | 1 | 0 |
| Original UI event 3 | 1 | 0 |
| Input tick | 5288→6346 | Unchanged |
| Completed frame serial | 13→18 | Remained 13 |
| Final versus starting screen | 3,790 pixels changed | Identical |
| Observation time | Virtual 200 ms | Virtual 200 ms |
| Guard and CPU/GPU faults | 0 | 0 |

Of 40 observed samples, 36 in the input run differed from the starting screen. All 40 no-input samples were identical. Each sample's raw byte size 165888 and SHA were checked. Direct PNG inspection shows the news card moving upward and the lower card border appearing. The rendered clock, fonts, and UI are generated by original ARM. This is not certification of physical optical output, performance, or pixel accuracy.

## Verification tools and boundary

`tools/run_active_hud_input.py --input-peer-ack --display-peer-ack` uses source-based response 4. The earlier response 2 can be explicitly selected with `--display-peer-reply 2`. At this stage the additional peer contract is allowed only for stock24 and is not automatically extended to older versions.

`tools/audit_active_hud_input_pair.py` reads saved input/no-input runs together. It checks identical main/model/board/activation/run/runner SHA and identical profiles except mode. It assesses file/plan hashes, CPU/time/SRAM preservation before and after actual input and response injection, source consumption order, task, stack, command payload, unchanged no-input screen, and changed input screen. It does not rebuild the model or execute ARM.

Only audit source was frozen and rerun from `/tmp` with empty PYTHONPATH; the report was byte-exact. Five semantic negatives based on original saved material were all rejected: missing input callback, different UI task, missing cleanup point, no frame effect, and changed no-input screen. Two new VMs were run, one input and one no-input. Removal of both owned containers and their actual Docker absence were confirmed.
