# Comparing Executors for Original Codec Code

Work `bw-0022` is limited verification for F4 and S2. Full firmware boot and display connection remain incomplete. The mismatch in execution including original initialization from the [upper-entry investigation](codec-update-ingress.md) was examined. No device connection, RAM payload, OTA, or permanent write occurred.

## Cause scope and cross-check

In Unicorn 2.1.4, connecting the original state wrapper, initialization, and getter caused state=2 to branch to another state instead of the codec check. The initialization function alone and a separate synthetic caller worked normally. In valid controls, removing the memory write hook made the original path branch as expected, while registering even an empty write hook reproduced the mismatch. The exact internal cause remains unknown. It is not interpreted as a firmware defect or physical-device behavior. Changing CPU model did not resolve it.

In some initial hook controls, subclass overrides were not applied to the actual instance returned by the Unicorn constructor. Those results were withdrawn; only instance-override tests recording actual registration/enabled status were accepted. Evidence is `verified-hook-isolation.json` and `write-hook-register-isolation.json`.

Independent review noted insufficient preservation of control-run code, so `tools/diagnose_codec_write_hook.py` preserves the configuration and reproduces three conditions. `reproducible-hook-comparison.json` records passing without hook registration, mismatch with empty/normal hooks registered, actual hook registration and invocation counts, and original probe and diagnostic code hashes. The no-hook condition isolates the cause and is not used as compatibility verification.

A path without write monitoring was not used as a completion criterion. `tools/run_renode_codec_ingress.py` and `tools/renode-codec-ingress.cs` executed the original state wrapper, initialization, and getter on native Cortex-M55 in the pinned Renode image. Preparation service, selector, file, transport, and codec-update bodies are outside execution scope.

For state=2, the CPU halted at codec check entry with force=0; otherwise it halted at the subsequent entry for another state. Final PC was checked against the boundary address. Original initialization cleared eight bytes on 2.3/CFW and nine on 2.4, retaining 0xa5 in four bytes on either side. All 12 conditions had >0 observed writes and 0 policy violations. Each condition ran sequentially in a separate container.

Containers used network none, 512 MiB, one CPU, 128 pids, removed capabilities, and read-only input mounts, with no USB or device connection. The pinned image is `sha256:e840c2b9a83dbf9be060047839aaaf6d434e7d4c52635191319afc14f4217649`. Guest writes are allowed only to fixture stack and initialization regions. This monitoring does not guarantee real-device protection or complete isolation of arbitrary malicious binaries.

## Correction of existing stub error

`emulate_codec_callers.py` was corrected to write the actual version-specific length after validating it, instead of always writing eight bytes. A new regression test uses a directly authored ARM wrapper and 0xa5 RAM fixture without proprietary images. Before the fix, the ninth byte remained 0xa5; afterward all nine were 0 and both guards were preserved. One regression test passed. This does not mean the earlier 21 cases were retroactively reverified.

Test source is `tests/fixtures/codec-init-wrapper.s`; generated bytes are in the same-named `.hex`. They were linked with LLVM 21 clang arm-none-eabi, cortex-m4, thumb and extracted with objcopy. Link address is 0x52af6a; absolute Thumb symbols are initialization=0x43c0e5, state_getter=0x465a5d, codec_check=0x59b49d, other_state=0x52af99. The literal pool aligns .text to 0x52af6c, so the test adds a two-byte NOP in front. Initial fixture address-alignment and overlap errors with the existing STRUCT region were corrected before the valid red test.

## Failed runs and remaining work

The first two native attempts ended at the 45-second limit before helper import; stage diagnostics in the third identified that boundary. Comparison with the existing runner led to correction of missing `clr.AddReference` in dynamic helper assembly. Next, the approach of throwing an exception at normal completion propagated the exception outside the address hook and terminated the process. Normal boundaries were changed to CPU halt and the PC checked. The final 12 conditions passed in a separate directory after these corrections. Earlier logs were preserved.

The Unicorn original-path mismatch is not claimed solved. The 48 stub-based conditions are not elevated to original execution. The native 12 conditions add separate evidence for the original state path. Actual boot conditions for automatic update, force input producer, write scope, and recovery remain unknown. Completion assessments and installation gate for F4, S3, full main boot, and integrated display remain unchanged.

Next priority is initialization paths such as D-cache geometry where full main stops (S3), continuing toward the full app loop (S6) and display boundary (D3).
