# Original AES-CMAC Requests and Subsequent UART1 Boundary

bw-0296. Analyzed original ARM functions beginning with the `2017` request in saved natural M55 states. No new natural M55 execution or physical device access occurred here.

## Operation confirmed

The pending request in all three firmware images had crypto state 1 and descriptor message length 494 bytes. Verified original queue-pop return pointer, descriptor, and message range in saved full SRAM. Compared every AES input generated by original code with an independent AES-CMAC reference calculation.

Each image matched 32 AES requests. The first AES processes a zero block for subkey generation; the remaining 31 process the message and final partial block. Checked key consistency, each plaintext, cryptographic result, and byte order. After the final 32nd response, original code delivered event `0x24` to owner 3 and reached the point where that handler reads UART1 status.

UART1 is not mapped in the isolated Unicorn function environment. All three inputs stopped at a four-byte read from `0x4003a018`, without supplying an arbitrary value. PCs were stock 2.4 `0x5ae038`, stock 2.3/Faceclaw `0x5ad92c`. Compared the [existing UART1 model evidence](../communication/uart1-model-proposal.md) and native-board port base to identify an FR read. This does not establish a persistent-memory write or full initialization success.

Original consumption of 32 cryptographic responses and completion-message creation were confirmed, but final owner-handler return, UART transmission, and subsequent app initialization were not yet confirmed. Verify this boundary with the existing UART1 model in the next natural M55 execution.

## Calculation method and byte order

`tools/bt_crypto_vectors.py` calculates one AES-128 ECB block using CommonCrypto `CCCrypt` on the current Mac. AES S-boxes/rounds were not reimplemented. Function signature, constants, and padding options were checked in local SDK `CommonCryptor.h`. Each 16-byte HCI key/plaintext is reversed for standard AES input; the result is reversed again for the wire response.

Compared HCI LE Encrypt format with a [distributed SIG specification §7.8.22](https://community.renesas.com/cfs-file/__key/communityserver-discussions-components-files/297/Core_5F00_v5.2.pdf), and byte order with `bt_encrypt_le` in [pinned Zephyr author source](https://pigweed.googlesource.com/third_party/github/zephyrproject-rtos/zephyr/+/5113c1418d2b9089be39a7e7dc6601f36e468193/subsys/bluetooth/host/crypto.c). Matching G2's 32 actual requests to CMAC reference inputs is additional execution evidence.

The CMAC reference constructs only standard subkey, padding, and CBC chaining; AES continues to use CommonCrypto. It passed the [preserved FIPS 197 Appendix C.1 test vector](https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.197.pdf) and [RFC 4493 §4 empty, 16-byte, and 40-byte CMAC vectors](https://www.rfc-editor.org/rfc/rfc4493.html#section-4). The FIPS document's 2023 revision notice states that the update was editorial without algorithm changes. Do not describe this research comparison as cryptographic-module certification.

CommonCrypto calculates results returned by a virtual Bluetooth controller; the EM9305 firmware binary was not executed. Apollo-side parser, crypto callback, and WSF handler are original ARM code. The engine is Unicorn M7 with synthetic entry, stack, registers, and verified native full SRAM. Distinguish this from natural M55 task scheduling.

## Control results

| Condition | Original subsequent behavior |
| --- | --- |
| Correct consecutive responses | Per image: 32 AES operations → owner 3/event `0x24` → UART1 FR read boundary |
| No response | No subsequent HCI request |
| First response status 1 | Generates next AES request |
| Incorrect opcode | No subsequent HCI request |
| Wire one byte short | No subsequent HCI request |
| Status 0 but cryptographic result replaced with 0 | Generates next AES request |

A subsequent request after error status or incorrect cryptographic result does not prove safe fallback, successful verification, or error recovery. Both controls cover only the first response; full initialization was not advanced with incorrect results.

## Verification and preserved assets

- Three images × six conditions, 18 scenarios. There were 96 correct AES blocks, 444 original function calls that returned, and three explicit final owner-handler UART1 boundaries.
- Four public AES/HCI/CMAC test methods passed in both working and frozen copies. Red failures for absent AES and CMAC helpers were confirmed first.
- Final source analysis is private `aes-initialization-source-06`. Reports, SRAM, WORK, and 38 files from `aes-initialization-source-07` using 48 pinned Python dependencies were byte-identical.
- Existing 30 SRAM/WORK files and return-call traces matched before/after adding the invalid-memory observer. Do not extend this control into a noninterference guarantee for all observers or hardware.
- Initial exploration limited to 16 iterations ended mid-operation and was not treated as complete. After identifying the 494-byte descriptor and distinct requests, the limit was raised to 64. Execution actually stopped at UART1 after the 32nd response.
- A report error caused by a message-variable name collision when storing reference metadata was fixed by separating names. Prior exploration and failure output were preserved, not counted as successful firmware stages.
- Four peripheral-model hashes matched the prior stage. There was no native main rerun or change to the web installer, recovery boot, or installation CFW.
