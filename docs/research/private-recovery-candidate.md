# Local-Only Recovery Bootloader Candidate

2026-11-10. Not installed on a device; actual compatibility unconfirmed; installation readiness incomplete.

A candidate using a new recovery key was built separately from the public-default-key research build. A git archive of pinned upstream commit `6198d70e18293caebf8314d2e40bd3b1d0a5ee16` was extracted into a dedicated directory outside Git and the official `make patch` was run. The build used LLVM/LLD 21 and Python 3 after checking the original 2.3.2.14 bundle SHA. The existing source checkout and research build were retained.

The new key is the UTF-8 hex string of a random 256-bit value generated by `secrets.token_hex(32)`. It was passed through upstream's `G2_BOOT_KEY` environment variable; actual device security settings were not accessed. The key file has mode 0600 and the dedicated preservation directory 0700. The actual image was checked locally for the corresponding HMAC key block. Do not put the key value in documentation, log output, or Git. The generated image and `auth_key.h` also contain the key and must not be publicly distributed or committed to Git.

Existing source-prefix, hook, raw-hash, padding, and receipt checks passed. Repeating the official `make patch` with the same key produced byte-identical output. An OTA header was generated with upstream `g2patch.firmware.component`, and its payload was confirmed identical to the original patched image.

Preserved at:
`~/Library/Application Support/Blackwall/recovery/private-boot-candidate-01/`

The directory contains source.tar, source/, recovery.key, stock-2.3.2.14.bin, build.log, rebuild.log, manifest.json, verification.json, and boot-recovery-component.bin. The manifest and verification store only an identifying hash instead of the key value.

- OTA component SHA-256: `08cdf7373de1fb60b2c2efa0afd5bec9702c0fa85ec63026b1fc1d19561b8368`
- OTA component bytes: 159872

The candidate's original boot remains 2.3.2.14. The user's actual boot/hardware/case, the combination with Faceclaw main, and full-main recovery were not verified. Generating a new key does not solve the boot protocol's challenge/replay or subsequent packet-authentication limitations. Losing the key prevents use of recovery access built with it, so a separate secure backup procedure is needed for the key exactly corresponding to the image. Actual recovery execution was not approved.
