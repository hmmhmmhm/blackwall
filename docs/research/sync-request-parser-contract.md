# Connecting Original Sync Requests to Byte-Stream Replies

bw-0362, E05/E13/E14. This connects the path where the original request API creates a correlation ID and reply record, and the original receive API's byte parser interprets a response to create a UI message. This is an **isolated M7/API test of three original images**. UART device input, natural M55 app startup, and phone BLE authentication remain unverified.

## Synthetic elements removed since bw361

The previous test directly prepared the callback descriptor and prior request context. This time the original allocator allocates the request node and packet, and the start/chunk/finish APIs used by the actual sending caller execute. Original code assigns the ID and records callback, timeout, and userdata in the reply record. The host does not construct the callback record or directly invoke the reply callback.

Transmission stops at the original transport leaf entry. The frame produced by the original code is compared with an independent encoder, and the same generated state is used as input to the receive test. This does not claim the sender's final return/lock release or physical transmission completed. Register/stack inputs between API calls are explicit isolated callers, not continuous natural RTOS execution.

Reception calls `SyncModuleReceivedDataHandler` from its original entry. That function reads the actual context slot and executes byte-array feed → byte parser → correlation-record lookup → master display reply callback → original UI producer. Normal reception returns to the receive API's original caller. Packet/node free and record removal by the callback also execute.

| Original boundary | Stock 2.4 | Other versions |
| --- | --- | --- |
| Request start API | 4b4102 | Found in each raw image through original callback-registration call |
| Chunk/finish API | 4b4114/4b411c | Compared adjacent wrapper instructions and BL |
| Receive entry | 468998 | Found through original feed call and actual context slot |
| Byte-array feed/parser | 4b3a36/4b3a80 | Found through instruction signature and BL |

Addresses are not merely added to an allowlist. Callback-registration literal, context slot, original wrapper, feed call, and allocator/deallocator BL are checked for each input.

## Frame contract

The original transmitted frame is:

`01 | ID(be16) | payload-length(be16) | channel(be16) | header-crc(be16) | payload | payload-crc(be16)`

CRC is a 16-bit calculation with initial value 0 and reflected polynomial a001. Header CRC covers the first seven bytes including the marker; payload CRC covers only the payload. When the payload is empty there is no trailing CRC. This encoder's output was compared with bytes produced by actual original start/chunk/finish. It is not assumed to share the public phone BLE eight-byte-header/CRC contract.

The virtual reply uses channel 2 and status-byte payload 2. The ID is generated by the original during that run. UI app ID, content, and length come from the earlier outgoing request and are not replaced by the received reply's content. The outgoing packet app header is a declared API fixture; its entire content was not authenticated as a phone-command format.

## Evidence of normal behavior

For three images, app 10b with zero- or four-byte payload and app 110 with 16-byte payload were each received in three ways: one batch, one byte at a time, and split header. This gives **27 normal deliveries**. The UI queue was empty before the final byte; after completion it contained exactly one `[2, app-id, length]`. Original queue receive/ring read recovered the exact original payload.

Observation runs confirmed the original deallocator's actual arguments were `[packet, node]`. Final receive return and reply-record removal were checked together. Whole RAM/WORK/SCS/final-register states with and without API/free-entry observation also matched for each normal input. This is a final-state comparison for those isolated inputs, not a general guarantee that native observers or RTOS scheduling have no effect.

## Failure and routing control limitations

Not all 54 controls establish fully successful failure handling. Their verification levels differ:

| Input | Actual observation | Remaining verification |
| --- | --- | --- |
| Modified header CRC | UI 0, record retained; stops at TIMER14 read in original diagnostic logging | Error-handler return and recovery to the next normal frame |
| Modified payload CRC | Same original diagnostic boundary, UI 0 | Handler return and recovery |
| Unregistered ID | No matching callback and UI 0; diagnostic boundary | Final return from unhandled-message path |
| Same ID, different channel 3 | **Original accepts it, produces UI 1, removes record, and returns** | Further review of complete security/protocol meaning |
| Redelivery of same reply | First input produces UI 1; second lacks record and remains UI 1 through diagnostic boundary | Final return from second handler |
| Timeout tick 50 | 49 returns; stops at TIMER14 access in 50th timeout diagnostic, UI 0 | Timeout cleanup, final late-reply handling, and real time |

The original dispatcher matches pending replies by ID; another channel did not block the callback on this path. Test expectations reflect that behavior; host channel validation was not added to change original behavior. This isolated observation does not establish an actual BLE vulnerability.

The error stop is original logging-function read32 `400083c0`. Stock 2.4 PC is 5070d4; TIMER14 is already supported by the pinned Renode board. An omitted isolated map is not reported as a G2 firmware defect. The timer was not arbitrarily zero-filled or the logger's return substituted; `failure_handlers_completed=false` was recorded. Of the 54 table cases, nine same-ID/different-channel cases returned normally; the other 45 are boundary evidence validating the above limitations.

## Next unit for actual board integration

When a separate stock 2.4 isolated send test continued beyond the transport leaf, the original reached UART0 DCR `40039048` write32 at PC 57f046. The pinned Apollo510 SVD defines this address as UART0 DMA control. The existing `BlackwallUartDmaTx` already supports this path. The UART number was not guessed from a name or task string.

Next, reuse the existing Renode board/API diagnostic recipe to execute UART0 DMA transfer/completion and TIMER14 error diagnostics. Then bind the UART0 RX device boundary, IRQ, and `uart_sync_thread`/receive callback registration from original code. The current UART adapter uses a PL011 backend, but its public RX injection/cause IRQ contract must be separately validated. Do not promote a direct callback call into RX device input.

Normal GAF service and natural main app-event conditions remain separately incomplete. This isolated step that omitted the sender leaf does not resolve those dependencies. E05/E13/E14 remain partial and overall progress is 4/16 = 25%. There were zero native runs, model changes, or physical-device accesses.
