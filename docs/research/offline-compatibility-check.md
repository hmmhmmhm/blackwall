# Offline Verification of Web Installation, Recovery Bootloader, and Faceclaw

Inspection date: 2026-11-10. User-approved scope: “check as much as possible without installing anything on the glasses.” No Bluetooth/USB connection, discovery, pairing, device RAM execution, persistent write, or OTA was performed. Only local builds, mock tests, and original-file analysis were performed. Nothing was published to GitHub.

## Objective and assessment at the time

The user-selected objective was **web flasher + g2-bootloader-patch for recovery + Faceclaw/g2flash-based Blackwall**. Reuse official-app communication where possible. Do not shift direction to avoiding CFW or building an independent iPhone app first.

**This configuration was not ready to install unchanged.** Local creation and validation of the bootloader and Faceclaw were possible, but browser installation support, version alignment with the 2.4 original, and physical compatibility of mixed main/boot/resources remained unresolved.

## Original and built-file checks

The [official CDN 2.4.0.24 bundle](https://cdn-az.evenrealities.com/firmware/a0d486afe862a9121657477b98667c95.bin) was downloaded and confirmed as 4,482,361 bytes / SHA-256 `363198f8d543a5c1181d8a213e9077285cb865700a1885c8dc7c1b9324fd0e05`. This is the distributed original, not a dump from the user's device.

| File | Confirmed SHA-256 / result |
| --- | --- |
| Boot payload in 2.4.0.24 bundle | 149,773 bytes, `ecb91896234392e2b98ec80b1ac3ebf4aa27726d3cbed10927edf0b44d83d665` |
| 2.3.2.14 boot required by recovery patch | 149,760 bytes, `22a2b98e606b4d296e957a3a8b600a2158497638d79485c817c2025536329ba7` |
| Locally generated recovery-boot research build | 159,744 bytes, `06f8a8d59f6351461aa9ce45cbc2a6697172cdca872ec77552325301ae175cc4` |
| Locally generated Faceclaw/38 bundle | 4,609,107 bytes, `4aac023f49ec6965186d9106e328a516f20a2915ab400d561f662f984023a432`, matching upstream expected output |

The recovery patch was generated by actually running upstream `make` and `make patch FIRMWARE=...` with LLVM/LLD 21.1.8, without modifying original or target source. It is a **research** file made with the public default HMAC configuration, not a build approved for installation. User security settings and keys were not changed.

Faceclaw's 39 committed patches were applied to the 2.3.0.24 original using upstream `patches/apply_patches.py`. Besides SHA validation, the source address inventory and 114 stock-byte guards in `audit_stock.validate_stock` were checked. This reproduces committed machine-code patches; it does not verify identical output after recompiling all C source from scratch.

Negative tests also ran. The boot tool's `extract_stock` accepted the 2.3.2.14 original and **rejected the 2.3.0.24 and 2.4.0.24 originals**. The g2flash patcher also rejected 2.4.0.24 because the original SHA did not match. No protection was removed and no new offsets were applied arbitrarily.

The actual g2flash `validate_firmware` accepted the 2.4 original and Faceclaw/38 result, each passing six component CRC checks and main preamble, destination, and size checks. Copies with the final payload byte flipped were rejected. The negative test attempting to patch the wrong 2.4 original produced no output file. All copies were local files.

Even if the user's main 2.4.0.24 matches the main version stated in boot-patch documentation, **the official 2.4 bundle's boot payload differs from the original supported by the patch**. Whether that bundle's boot is installed on the actual device is unknown. Separately installing 2.3.2.14 boot and mixing it with 2.4 main is also not classified as a safe downgrade.

## Mock tests performed

| Check | Actual result | Evidence limitation |
| --- | --- | --- |
| Initial upstream boot unittest run | 115 executed, zero assertion failures, one host crypto class setup error | Upstream `-nostdlib/-fuse-ld=lld` shared-library link failed on Mac. Do not report the unmodified full suite as passing |
| Full run after host-only boot build adjustment | **118 passed**, zero skipped, zero errors | Only host crypto compilation used Apple clang + system runtime. Firmware, test assertions, and ARM emulation code were not changed |
| WebFlasher `g2-ble-ota.test.mjs` | **29 passed** | Fake GATT/chooser checked ACK, NAK, timeout, reconnection, topology, and concurrent sessions. Not an actual radio test |
| WebFlasher browser/recovery-defaults/automatic-recovery | **60 passed** | Mock environment; not physical evidence of case/glasses boot or recovery |
| Recovery CLI file validation | Faceclaw/38, stock 2.3.0.24, and stock 2.4.0.24 all **passed local input validation** | Run without `--write`. Acceptance of input structure is not firmware interoperability validation |

The boot test runner included barriers forbidding serial open and Bleak connect/scan. There were zero actual access attempts blocked during execution. Writer, checksum, handoff, stream, CRC, watchdog, and authentication ran in virtual memory, not in glasses or case RAM.

Host crypto diagnostics also retained two intermediate failures. With dynamic lookup alone, the macOS loader rejected the library because the libSystem load command was absent; adding libSystem with LLD 21 failed because it could not read the newer macOS SDK TAPI architecture. The assumption that Linux-style freestanding shared-build options must be retained was dropped, and **only the host test library** was linked with Apple tools and the system runtime. Do not erase this distinction or report it as an unmodified upstream-suite pass.

## Browser decisions on actual files

WebFlasher production `parseFirmwareInput` and `assertPinnedG2BleBundle` were called on actual local files. No hardware methods were called.

| Input | Production decision |
| --- | --- |
| Stock 2.3.0.24 | Structure and pin checks accepted |
| Stock 2.3.2.14 | Structure and pin checks accepted |
| Stock 2.4.0.24 | Structure readable, but BLE write rejected because there is no catalog pin |
| Faceclaw/38 bundle | Structure readable, but BLE write rejected because there is no pin |
| Generated raw recovery boot | Rejected as an unsupported file format |

The public browser path at the time required installation of an exactly pinned **complete six-component bundle**. It had no ready-to-run boot-only or main-only mode. Mock tests also confirmed the default target was both sides. Thus a workflow of “find the web tool and click to install the recovery boot first” did not yet exist.

Upstream Python `tools/flash.py` has boot-only OTA, but this is not equivalent to WebFlasher's implementation. This does not mean a browser is technically incapable of BLE OTA; it means a web path implementing and verifying the required single component, side, exact artifact, and validation contract did not yet exist. Do not remove existing pin, format, or confirmation protections to make it pass.

## Boot preservation and stock restoration

| Region | Research-build range (end exclusive) |
| --- | --- |
| Patched boot | `[0x00410000, 0x00437000)` |
| Faceclaw/38 main | `[0x00438000, 0x007DF048)` |
| Stock 2.4.0.24 main | `[0x00438000, 0x007BF564)` |

Upstream `recover.py` writes only the main region in default app mode. There is evidence that this preserves boot **by address range**. However, it requires an already functioning patched boot, and upstream had not physically validated full-main recovery. Existing WebFlasher reinstall through a running main and this recovery protocol differ; no browser implementation of the latter was identified.

The full Faceclaw bundle contains stock 2.3.0.24 boot, so OTA of the complete bundle risks losing recovery boot. Conversely, replacing main only requires validation of mixed external resources and subordinate components. Actual 2.3.0.24 and 2.4.0.24 codec payload hashes differ, while BLE/touch/case payloads match. Do not extend main-only success to normal operation of all stock app, sensor, and audio functions.

Stock 2.4 main passed file validation, but actual boot under patched boot and compatibility with current NOR resources were unknown. Full-stock restoration requires restoring boot as well and verifying that additional written pages are restored. A stock boot prefix hash alone does not verify absence of remaining appended code. Restoring boot removes the self-recovery path; it was neither approved nor physically validated.

## Can the official app control Faceclaw functions?

Current g2flash `message_transport.h/.c` implements a private **SID 0xF0** record/CRC/ACK path connected to resource/draw/root-list/PRESENT commands in `zlib_glue.c`. Faceclaw Kotlin `CfwTransport.kt` uses the same SID. This is not the same transport contract as the official app's ordinary text/image container API.

[Faceclaw extension documentation](https://github.com/jimrandomh/faceclaw/blob/70ec2a0d6afd92e8185234e57ab013fcb596bf4d/evenhub-extensions/README.md) states that the official app lacks the extension host API. The objective of reusing normal official-app functions remains, but **installing CFW alone does not mean the official app will send Faceclaw display lists**. First design whether a verified adapter is possible through the official SDK or a separate minimal transport is required. Do not expand this into a reason to build a large companion immediately.

## Three questions for subsequent design

1. **Select the supported boot baseline:** After identifying actual boot later, determine whether the current 2.3.2.14 supported path can be used or current 2.4 boot support is needed. Do not recommend a downgrade solely because local tests passed.
2. **Web installation path:** Based on upstream boot-only procedures, design a web adapter preserving exact per-component pins, one-side targeting, confirmation, and readback, plus main-only/stock-restore modes. A local file inspector was added; a web writer was not yet implemented.
3. **Runtime transport:** Decide how to reach private CFW features while preserving standard official-app features. Distinguish stock SDK experiments from Faceclaw extension experiments.

The recommendation at the time was **defer hardware installation and continue design/mock verification of these three interfaces**. This does not abandon the user's selected configuration; it identifies work needed to make it safe.

## Additional confirmation and rerunnable local inspectors

In [Faceclaw issue #56](https://github.com/jimrandomh/faceclaw/issues/56), author jimrandomh explained on 2026-10-31 that a downgrade path from 2.4.0.24 to current Faceclaw is supported. The author also noted that returning to the official app presents a 2.4 update and some official-app features may not work until updating. On November 1 the author stated that app 0.8.6 onward removed the untested-version warning for that version. Classify this as an **author explanation and source support**, not validation on the user's device. Based on this evidence, a complete 2.4-based Faceclaw port need not be the starting point. The combination of separate recovery boot and main-only installation remains unknown.

`tools/blackwall_package.py` and `tools/audit_assets.py` inspect files only. They do not import or execute Bluetooth, USB, serial, or OTA transport. They check exact SHA for three originals and generated CFW, 24 component CRCs, main destination/vector/range, and recovery boot original prefix, three hooks, branch targets, page padding, and build receipt. The receipt is not a signature, and its key identifier is self-reported. These checks alone do not certify build provenance, device compatibility, or matching security keys.

The CLI passed using six actual research files: three originals, CFW, patched boot, and receipt. Results are in [offline asset audit JSON](../data/offline-asset-audit.json). `readyForHardwareInstall` is **false**. A main-only operation descriptor is data for reviewing hashes and allowed components, not an executable installation command or repackaged image.

Blackwall's own `python3 -m unittest discover -s tests -v` had **11 tests pass**. Rejections checked included payload mutation, component bounds, filenames, main destination, mixing boot and main operations, and missing boot-key metadata. This count is separate from the upstream tests above. The research boot's public default HMAC key was also recorded as an installation blocker.

In additional actual-file negative tests, substituting another official version for `stock-current` made the CLI exit 1 due to SHA mismatch. Three copies each changing one bit in original bytes outside boot hooks, appended code, or padding were all rejected. Copies were mutated only in memory. The Git working folder was also checked for absence of `.bin` files and MIT notice identity with the original.

Rerun example (supply actual firmware locations; outputs JSON only):

```sh
python3 tools/audit_assets.py \
  --stock-base /private/recovery/stock-2.3.0.24.bin \

  --cfw /private/recovery/faceclaw-38-research-only.bin \

```
