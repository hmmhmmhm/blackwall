# UI entry through virtual touch and UART from the original bootloader

bw-0546. After running stock 2.4 boot→main on the same board for 20 seconds, prepared GPIO27 received low, then high after one virtual millisecond. One original IOM5 touch-frame consumption/four chunks and actual UART requests were confirmed. Guest PC/TCB/queue/readiness/memory were not directly written.

At the first 5 ms, CRC/length of actual channel 1 request IDs 0x800d/0x800e were checked and channel 0/type 10 ACKs placed in UART0 FIFO for each. Responses are not fabricated from descriptors before original transmission. Five milliseconds of observation after the first response retained a bounded failure because the app request had not appeared during receive handling; this does not establish communication failure. Extending to the existing original path's 100 ms processing interval produced actual channel 2/ID 0x8010/payload `0201010000000000`. A type 2 response was supplied only for that ID. Intermediate ID 0x800f was an original proximity-release report and received no arbitrary additional ACK.

CPU R0–15, instruction count, and virtual time were identical immediately before/after input. Touch accepted/released, three UART responses accepted, and final RX 36 bytes/pending 0 were confirmed. Original UI dispatch 0x4456e8 and app 1 callback 0x4b7a58 each ran once. After another 500 ms, PC 0x44eb9c/current ui_task, renderer 0/frame 0, guard/fault 0. Thus UI entry is confirmed but callback completion and a completed display remain unconfirmed.

Key RAM evidence from the successful 100 ms run remains. Two owned containers confirmed removed. Source, pinned manifest, reproduction commands, wire JSON, and failure/success logs remain. Overall 5/8=62.5% remains.
