# Time-based detailed boot observation and report

bw-0600. In response to the user's request to improve observation gaps, a separate observation profile `tools/prepare_detailed_boot_profile.py` was added without changing bw595's pinned original boot/main model. It records virtual-clock samples in the existing UART1 output callback and timestamps existing UART0 DMA transfers. Byte capture capacity/drops follow existing UART limits. Guest registers, memory, firmware branches, and existing experimental profile are unchanged. No `SyncTime()` was added.

A normal stock 2.4 virtual experiment captured 2,451 original UART1 bytes and 2,451 timestamps (drop 0), 21 UART0 DMA transfers/693 bytes (drop 0), three GPU frames, and PC observations. Complete UART0 DMA bytes matched the original UART0 buffer in the same run. UART1 ANSI display controls remain in raw data but are removed from HTML. Line time is the virtual-clock observation of its final byte; TX time is model transfer-capture time. These are not actual baud or physical bus precision. The report displays UART1 logs, UART0 packets, and UI/frames at corresponding times, adding NOR/filesystem/BLE reporting points to boot stages. U25643 placement in the NOR model is an estimate based on an FCC sample and represents the related part in firmware logs; it does not guarantee that physical hardware uses it or initialized successfully. The relevant side is selected automatically until the user rotates it.

Normal and unknown-marker runs were each newly executed and passed independent audit. Boot PC order, end location, complete original UART bytes, and wire requests/responses were compared against previous bw595 run; fault 0, sorted UART1 timestamps, and overflow 0 were confirmed. Normal handoff context and final guest framebuffer match within the same run were also checked. This does not prove equivalence of all internal states or actual hardware. Evidence is in `private:simulator/detailed-boot-observer-bw601/comparison.json`, `detailed-boot-normal-bw601-01`, `detailed-boot-negative-bw601-01`, `report-bw600-integrated`, and `report-bw600-final`. Code, optional profile, and audit manifest remain; three reproducible temporary reports totaling 17,088,883 bytes were cleaned up.

## 12-second early-input test

The pinned baseline 20-second observation was preserved. In separate research copy `tools/prepare_short_boot_observation.py`, only the initial observation window was changed to 12 seconds. This is not an official profile changing the original runner's 20-second budget; actual experimental value is recorded as `profile.experiment.observation_window_us`. In this experiment input was accepted/released, but neither expected UART request appeared during the subsequent 5 ms observation, so original scenario semantic verification failed. This is not a corruption/flash/physical safety failure and does not establish its internal cause or that 12 seconds fails in every run. Evidence remains in `private:simulator/short-boot-experiment-bw600-01`, independent audit, and `private:report-bw600-short`. The normal 20-second setting was not replaced. The failure report shows actual error and occurrence time.

## Scope and verification

Chrome at 1440×900/390×844 was used to check NOR log and corresponding model at 3 seconds, BLE log near 12 seconds, UART0 transmission, time filter/latest scroll, expected stop, and 12-second failure report. Twenty-two related units passed. Log labels are English. Complete chip state over time, all IRQ/power/sensor/GPU internals, actual component identity, arbitrary CFW support, and precise physical time remain incomplete. The experiment report's share link is the temporary Cloudflare tunnel requested by the user; it does not expose original firmware images or raw private folders.
